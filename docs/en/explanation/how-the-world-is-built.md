# Explanation: how the world is built

Open the scene in the editor and you find one object, `Bootstrap`. There is no
level to look at. Everything – the car park, the sky, the lights, the players,
the farts, the menu – is created by code in the first frame. This page explains
why, and what follows from it.

## One description of the arena

The car park is defined by a handful of constants in `Arena`: how many decks,
how far apart, where the ramps start and end, where the holes are. Three very
different pieces of code read them:

- `ArenaBuilder` makes the slabs, ramps, railings and colliders;
- `GameBootstrap` decides where farts may lie;
- the bots (`AICompetitor`, `NavPlanner`) decide where they can walk.

If the level were modelled by hand, the bots' idea of it would be a second
copy that drifts away from the first with every edit. Built from shared
numbers, the world the bots plan in *is* the world that gets built. Change
`RampWidth` and the ramp, its kerbs, its hole in the deck above, the railing
round that hole and the bots' path all move together.

The same property makes two-player simple: both devices build an identical
arena without exchanging a single triangle, so the network only has to carry
what moves.

## Big flat things are generated, detailed things are models

Slabs, ramps, kerbs and beams are boxes produced by `MeshFactory`, with texture
coordinates in real metres so that a concrete texture has the same scale on a
26 m deck and a 30 cm kerb. Things with shape – a railing section, a column, a
lamp, the goal, the competitors, the monster – are FBX models, themselves
generated by Blender scripts, and are placed along the grid.

Code finds parts of a model by name ("GoalFan", "MonsterJaw") and swaps every
material slot for one of the project's own materials. Models therefore carry
no textures and no look of their own; the look lives in one place,
`GraphicsSetup`.

## Materials are generated too

`GraphicsSetup` writes every material the game loads. This is not tidiness for
its own sake: Unity only puts into a build the shader variants that some asset
needs. A material invented at run time would work in the editor and come out
pink in a build. Generating the materials as assets, from one script, keeps
editor and build identical, and makes "what does the game look like" a file one
can read and diff.

## Light

The aim was a scene that reads as a photograph of a real place rather than as
a game level:

- The sky is a photograph (an HDRI). The sun is a directional light placed
  exactly where the sun is in that photograph, so shadows agree with the sky.
- Nearly all play happens under a concrete slab. Light there arrives sideways
  through the open edges and bounces off sunlit floor, so the ambient light is
  a hand-tuned three-colour gradient instead of the open sky's.
- Each deck has one reflection probe, captured once when the world exists, so
  glossy floors reflect the room they are in and not the sky.
- Tone mapping, bloom and a little grading are applied to the scene only. The
  HUD is drawn afterwards, untouched.

`LightingRig.SetMood` can slide all of this – sun, sky, ambient, fog,
reflections, colour – from the sunny day to a green gloom. That one dial is
what the monster turns.

## Input in one place

`GameInput` is the only code that knows whether a keyboard or a touch screen is
in use. The player code asks "which way?", "jump?", "blast?" and gets the same
kind of answer either way. On touch screens each control keeps the finger that
started on it, which is what lets you walk, look and press a button at once;
and because fingers come in through one small interface, a test can feed in
scripted ones.

## What this approach costs

- Nobody can nudge a prop in the editor. Every change is a code change, looked
  at through screenshots.
- The first frame does all the work. On a computer that is a third of a second;
  it is logged (`[Boot]`) because on a slow phone it may not be.
- The scene file tells a newcomer nothing. Start reading at
  `GameBootstrap.Awake`.

For this small game the trade is a good one: one person can hold the whole
world in a few constants, and the same build can be exercised without a screen
([Testing without a screen](testing-without-a-screen.md)).
